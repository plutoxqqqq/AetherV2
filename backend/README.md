# AetherV2 backend services

The backend contains the private source proxy, the persistent key registry, the Discord key-management bot, and the older config-review service.

## 1. Key-gated private source proxy

### What it does

1. A loader contains a random key.
2. The loader reads the executor's Roblox username and UserId.
3. The proxy verifies that username/UserId pair with Roblox.
4. On first use, the key is locked to that account in backend/key-bindings.json.
5. A different account using the same key is rejected.
6. A short-lived session is required for init.lua, the source tree, commit checks, and client files.

The raw key is never stored in the registry. The registry stores a SHA-256 key ID instead. The proxy also logs the key ID prefix, username, and UserId rather than logging the secret itself.

This protects the source while it is stored in GitHub. It cannot make code impossible to copy after an authorized executor receives it, and a modified executor can spoof client-reported identity. Keep the existing owner lock as a second runtime check.

### Source proxy environment variables

Use a fine-grained GitHub token limited to this repository with Contents: Read and write:

~~~
GITHUB_TOKEN=github_pat_...
GITHUB_REPO=plutoxqqqq/AetherV2
GITHUB_BRANCH=main
AETHER_SESSION_MINUTES=120
PUBLIC_ORIGIN=https://aetherv2.onrender.com
~~~

AETHER_KEYS is optional now. It remains a legacy/bootstrap list of comma-separated keys:

~~~
AETHER_KEYS=old-key-1,old-key-2
~~~

New keys generated by Discord are stored in the private registry and do not need to be added to AETHER_KEYS. After migrating old keys into the bot, you can remove AETHER_KEYS from Render.

Optional:

~~~
AETHER_AUDIT_LIMIT=500
~~~

The first registry write requires GitHub Contents: Read and write. Do not put GITHUB_TOKEN or raw keys in Lua, GitHub files, Discord channels, or committed environment files.

### Render deployment

The proxy and Discord bot run in the same Node process, so one Render service is enough:

1. Create a web service from the private plutoxqqqq/AetherV2 repository.
2. Set Root Directory to backend.
3. Set Build Command to npm install.
4. Set Start Command to node private-source.js.
5. Add the source-proxy variables above.
6. Add the Discord variables from the next section if you want the bot enabled.
7. Deploy.

Without DISCORD_TOKEN, the source proxy still runs normally. With DISCORD_TOKEN, the same process also connects the Discord bot.

Render's free service can sleep or restart. The GitHub registry survives, but in-memory loader sessions disappear, so users may need to run their keyed loader again. A Discord bot on a sleeping free web service may also temporarily disconnect. An always-on host is better if the bot must respond continuously.

### Per-person loader

Generate a key, then give the person a loader containing that key:

~~~
loadstring(game:HttpGet(
    "https://aetherv2.onrender.com/loader?key=ASSIGNED_KEY",
    true
))()
~~~

The repository's loadstring file is also a template that can use getgenv().AetherV2SourceEndpoint and getgenv().AetherV2Key.

## 2. Discord key-management bot

The bot is owner-only. It does not use Discord display names for authorization. It checks the immutable Discord user IDs listed in DISCORD_OWNER_IDS.

### Discord environment variables

Add these to the same Render service:

~~~
DISCORD_TOKEN=your_bot_token
DISCORD_APPLICATION_ID=your_application_id
DISCORD_OWNER_IDS=your_discord_user_id,optional_second_owner_id
DISCORD_GUILD_ID=your_server_id
~~~

DISCORD_GUILD_ID is recommended because commands register in that server immediately. If it is omitted, commands register globally and Discord may take a while to make them appear.

Never commit DISCORD_TOKEN. If it is exposed, reset it immediately in the Discord Developer Portal.

### Create the Discord application

1. Open the Discord Developer Portal.
2. Create a new application.
3. Copy its Application ID into DISCORD_APPLICATION_ID.
4. Open the Bot page and create/reset the bot token.
5. Copy the token into Render as DISCORD_TOKEN.
6. Enable Developer Mode in Discord, then copy your own user ID.
7. Put that ID in DISCORD_OWNER_IDS.
8. Invite the bot to your server with the bot and applications.commands scopes. It only needs basic slash-command access; do not give it Administrator permission.
9. Add DISCORD_GUILD_ID for the server where you want the commands.

A simple invite URL is:

~~~
https://discord.com/oauth2/authorize?client_id=APPLICATION_ID&scope=bot%20applications.commands&permissions=0
~~~

Replace APPLICATION_ID with the Discord application ID.

### Commands

All commands are slash commands under /key:

* /key generate — creates a new random key. It returns the raw key and loader once in an ephemeral response. The raw key is not saved and cannot be displayed again.
* /key list — lists key ID prefixes, labels, status, expiry, binding, and usage count. It never lists raw keys.
* /key info key_id — shows full details for one key. key_id can be the full ID or a unique prefix.
* /key edit key_id — changes the label, expiry, or enabled state. key_id can be the full ID or a unique prefix. Use none for a label or expiry to clear it.
* /key unlink key_id — removes the username binding so the key can be claimed by another account. key_id can be the full ID or a unique prefix.
* /key unlink username — finds and removes a binding by Roblox username. If more than one key matches, use key_id instead.
* /key revoke key_id — disables a key without deleting its history. key_id can be the full ID or a unique prefix.
* /key enable key_id — re-enables a revoked key. key_id can be the full ID or a unique prefix.
* /key rotate key_id — disables the old key, creates a replacement, and transfers its current binding. key_id can be the full ID or a unique prefix.
* /key audit — shows recent generation, binding, edit, unlink, revoke, enable, and rotation events.

The raw key appears only in an ephemeral Discord reply. Treat it like a password and send it privately to the intended person. Management commands accept a unique key-ID prefix, so you do not need to copy the full 64-character hash from the registry.

### Key lifecycle

A normal workflow is:

1. Run /key generate label:CustomerName.
2. Copy the raw key and loader from the private ephemeral reply.
3. Send that loader only to the intended person.
4. Use /key list to copy a key ID prefix, or use the full ID returned by /key generate.
5. The first run binds the key to that Roblox username/UserId.
6. Use /key info to inspect it later.
7. Use /key unlink if you want the same key to be claimed by someone else.
8. Use /key revoke if the key was leaked.
9. Use /key rotate if you want a replacement while preserving the existing binding.

Unlinking does not create a new raw key. It simply removes the existing binding; the next successful authorization can bind that key to a different account. A revoked or expired key must be enabled again before it can be used.

The registry keeps a bounded audit history and is committed to the private repository through the GitHub Contents API. A first use or bot action creates a GitHub commit.

### Migrating existing AETHER_KEYS

Existing environment keys are recognized automatically. They appear in /key list as Environment key. You can use /key edit, /key unlink, /key revoke, and /key rotate on them; the bot will create a registry record that overrides the environment default.

After confirming the migrated keys work:

1. Revoke or rotate any old keys you no longer want.
2. Remove AETHER_KEYS from Render.
3. Use /key generate for all future keys.

This makes Discord the main key-management system.

## 3. Config-review backend

The separate config-review service stores submissions, rejects identical config payloads, exposes an authenticated review queue, returns decisions to uploaders, and publishes accepted configs through GitHub's Contents API.

### Local setup

~~~
cd backend
export ADMIN_KEY='paste-the-random-maintainer-key'
export GITHUB_TOKEN='github_pat_...'
export GITHUB_REPO='plutoxqqqq/AetherV2'
export GITHUB_BRANCH='main'
export DATA_FILE="$PWD/data.json"
npm test
npm start
~~~

The review service needs a persistent DATA_FILE in production.

### API contract

* POST /submissions validates metadata and config data.
* GET /submissions?status=pending requires Authorization: Bearer ADMIN_KEY.
* GET /submissions/:id?token=receipt lets an uploader retrieve their outcome.
* PATCH /submissions/:id accepts an authenticated accept or reject decision.
* DELETE /public-configs removes a known public config after admin authentication.

For production, monitor HTTP 5xx responses, back up DATA_FILE, keep Node patched, restrict Render dashboard access, and rotate secrets immediately if exposed.
